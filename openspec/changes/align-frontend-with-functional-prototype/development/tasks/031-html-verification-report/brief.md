# Task Brief: 031-html-verification-report

## Goal

Produce the stakeholder-facing SpecNav HTML verification report covering every
completed acceptance assertion (A1-A4 in their task-scoped sense) and every
verified route row of the 67-row parity matrix, with the blocked repository
row `4` explicit, as three self-contained HTML pages plus the report model and
render manifest, generated by a replayable script over the executed evidence.

## Vertical Slice

Close baseline task `8.3`: generate the HTML verification report with
evidence for every completed assertion and route row from the executed
six-domain evidence, keep blocked row `4` explicit, and bind the generated
pages in a render manifest.

## In Scope

- Build `evidence/build_html_report.mjs`: a replayable generator that reads
  the change acceptance, the six-domain summary (Task `030`), the 67-row
  parity matrix, the per-slice acceptances (`001-030`), and the validation
  log, and writes:
  - `verify/reports/overview.html` — aggregate verdict, six domains, assertion
    coverage, blocked row 4 banner;
  - `verify/reports/test-case-catalog.html` — every route row with status,
    evidence references, and per-slice evidence inventory;
  - `verify/reports/test-case-results.html` — per-slice acceptance results and
    executed receipts;
  - `verify/v2/report-model.json` — the data model binding the aggregate,
    readings, and evidence index;
  - `verify/v2/report-render-manifest.json` — the three HTML paths with
    sha256 hashes and sizes.
- Verify the pages are self-contained (no external assets) and render (spot
  check with the headless browser: title, row count, blocked row 4 present).
- Close only baseline task `8.3` after both reviews pass.

## Out Of Scope

- The final parity declaration (task `8.4`), parent acceptance, and archive.
- Reopening blocked repository-add row `4`.
- New production behavior, routes, APIs, or fixtures.
- Running the V2 `dsh-verification-adapter` lifecycle (no V2 case snapshot
  exists; this is documented rather than simulated).

## Components To Create

- No production component is planned; create only the report generator under
  the task's `evidence/` directory.

## Components To Reuse

- The six-domain summary and per-slice acceptance artifacts; no production
  code is touched.

## Components To Extract

- No extraction is needed; the generator is a thin script over existing
  evidence files.

## API / Data Flow Contracts

- No production change; the report is generated from executed evidence.

## State / Error / Empty / Loading Behavior

- The generator fails closed if a required evidence file is missing or its
  summary says not-ok.

## TDD Requirement

- The generator's output must contain exactly 67 matrix rows with row 4
  marked blocked, all four assertions with their verified state, and the
  three HTML pages must hash-match the manifest.

## Verification Commands

- `node openspec/changes/align-frontend-with-functional-prototype/development/tasks/031-html-verification-report/evidence/build_html_report.mjs`
- Headless browser spot check of `verify/reports/overview.html`.
- SpecNav entry and handoff contracts with `OPENSPEC_TELEMETRY=0`.

## Stop Conditions

- Scope lock mismatch.
- A required evidence file is missing or not-ok.
- The generator output would claim parity for blocked or unverified rows.
- Closure would complete task `8.4`, row `4`, or parent acceptance.

## Unsafe Assumptions

- The V2 adapter lifecycle is not run; the report is generated from the
  executed development evidence, and this decision is recorded in the report.
- A rendered page implies content truth only insofar as the generator reads
  the executed evidence files without transformation.
